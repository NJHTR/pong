# Real Multi-Agent E2E Experiment

**Status:** `EXPERIMENT PREPARATION / PROVIDER-GATED / PROTOCOL-FROZEN`

**Baseline:** `5a88715 feat: add local agent bootstrap discovery`

This document is an operator-run experiment plan for two independent Agent
Runtime processes, such as Codex Code and Claude Code, using one Pong Core.
It does not add a provider adapter, modify `seekwd`, or claim that a provider
run has passed. The current M4-021 gate remains `BLOCKED / PROVIDER ENVIRONMENT`
until a current-HEAD run records successful real Codex and Claude invocations.

## Scope And Boundaries

The system under test is:

```text
Codex Runtime ───────┐
                     ├── Pong Core ── durable Repository / Workspace state
Claude Runtime ──────┘
                     │
                     └── D:\bs\seekwd filesystem Workspace
```

`seekwd` is only a filesystem project. It does not import a Pong SDK, call the
Protocol, or implement an Agent Runtime. Each provider must be a separate OS
process and must reach Pong through the existing transport adapter.

Do not change during this experiment:

- `D:\bs\seekwd` source or configuration;
- External Agent Protocol v1.0;
- Core schema, Repository policy, or lifecycle semantics;
- provider credentials or provider-specific adapter code;
- Exploration, Candidate, Route, Evaluation, Selection, Change, Branch, or
  Push models.

The experiment records evidence. Pong remains authoritative for durable IDs,
leases, revisions, Operations, Versions, Checkpoints, Handoffs, Resumes, and
cold-reopen state.

## Common Procedure

1. Confirm the operator is in `D:\bs\seekwd` and that the bootstrap file is
   present and readable without editing it.
2. Resolve the bootstrap descriptor from the project cwd. Record the resolved
   Repository and Workspace references, Protocol version, and endpoint.
3. Start one Pong Core according to the selected transport. For local JSONL,
   the adapter process owns one Repository; for concurrent independent clients,
   use the existing local HTTP transport or another already-supported broker.
4. Start Codex and Claude as separate provider processes. Do not reuse a
   process, stdin/stdout session, credential session, or in-memory client
   object between them.
5. For each Runtime, record the provider's logical `agent_id`, OS PID, process
   start time, transport session identifier if available, and a local
   `incarnation_id` generated by the experiment harness. Pong Protocol v1.0
   does not persist a separate process-incarnation entity.
6. Run `hello` first and record the advertised Protocol version and capability
   list. Register each logical Agent with `register_agent` and verify that the
   two Agent IDs differ.
7. After every mutation, record its request/Operation identity and the durable
   response IDs. On every reconnect, use queries against Pong rather than
   provider memory.
8. At scenario end, close both provider processes cleanly when possible and
   record the Core/Repository cold-reopen observations.

## Scenario A: Independent Bootstrap

### Steps

1. Codex enters `D:\bs\seekwd`, resolves the nearest `.pong/bootstrap.json`,
   connects to Pong, calls `hello`, and registers Agent A.
2. Codex confirms the existing Repository/Workspace and creates Task T1 and
   Execution E1.
3. Claude independently enters the same directory and resolves the same
   bootstrap descriptor. It starts a new provider process/incarnation, calls
   `hello`, and registers a distinct Agent B.
4. Claude queries the same Workspace and Task, then creates its own Execution
   only if the scenario requires a second run.

### Acceptance

- Both Runtime resolutions identify the same Repository reference and
  `workspace_id`.
- Agent A and Agent B are different durable identities.
- Runtime/session/incarnation observations are different.
- E1 is owned by Agent A; any Claude Execution is owned by Agent B.
- No provider relies on the other provider's memory or local cache.

## Scenario B: Codex To Claude Handoff

### Steps

1. Codex continues from Scenario A with Task T1 and Execution E1.
2. Codex performs a controlled `publish_version`, creating V1, then creates
   Checkpoint C1 and Handoff H1 using the existing Protocol commands.
3. Stop or disconnect the Codex Runtime without deleting Repository state.
4. Claude discovers bootstrap metadata, registers Agent B, queries T1/C1/H1,
   and calls `resume_from_checkpoint`.
5. Verify the resume creates a new Execution E2 owned by Agent B. Claude makes
   its controlled workspace change and publishes V2.

### Acceptance

- C1 provenance and source Version are unchanged.
- V2 has the expected parent/base relationship and is not an overwrite of V1.
- H1, resume, and publication Operations have the correct owners.

## Scenario F: Pong Core Restart

### Steps

1. With both providers holding durable Task/Execution/Version/Checkpoint
   history, record the Core PID/incarnation and close the transport according
   to the selected adapter's shutdown procedure.
2. Stop the Pong Core. Do not delete `.pong`, Repository storage, or Workspace
   bindings.
3. Restart the Core against the same Repository and binding root. Record the
   new Core PID/incarnation.
4. Restart or reconnect Codex and Claude independently from the same project
   cwd. Each resolves bootstrap metadata, creates a new transport session,
   and re-authenticates if the transport requires it.
5. Query the existing Task, Executions, Versions, Checkpoints, Handoffs, and
   Operations from Pong. Resume only through the existing Protocol semantics.

### Acceptance

- Both Runtime histories are present after Core restart.
- Repository and Workspace identities are unchanged.
- New transport sessions/incarnations are distinct from the old ones.
- Queries and recovery use durable Core state, not provider memory.
- No duplicate Task, Workspace, Version, Checkpoint, or Operation is created
  by reconnect.

## Result Classification

Use exactly one result per scenario:

- `PASS`: all acceptance assertions passed and the evidence ledger contains
  real IDs and runtime observations.
- `FAIL`: Pong or the transport violated an acceptance assertion. Include the
  smallest reproducible request sequence and all relevant IDs.
- `BLOCKED`: the provider process, credential service, model channel, host
  capability, or other external prerequisite prevented the scenario from
  reaching its acceptance point. Include the provider error verbatim after
  redaction, the last completed step, and the IDs that do exist.

Provider HTTP 403/503, quota exhaustion, unavailable model channels, and
missing authenticated Codex/Claude CLIs are `BLOCKED / PROVIDER ENVIRONMENT`,
not Pong Core failures. Do not substitute a mock provider or mark an
unexecuted scenario `PASS`.
